# pyfix-rl — Scope Note

## What the Agent Does

The agent interacts with a **code-repair reinforcement learning environment**.
In each episode, the agent is shown a short Python function that contains one or more
deliberately introduced bugs. The agent submits a corrected version of the function as
a plain string. After each submission, the agent receives:

- A **binary reward** (1.0 if all hidden tests pass, 0.0 otherwise).
- A **sanitised error summary** — the exception type and one line of traceback from
  within the submitted code. No expected values are ever revealed.
- The **previous submission** — so the agent can refine its fix based on what failed.

The agent gets up to **three attempts per episode**. The episode terminates when the
agent produces a correct fix (`terminated = True`) or exhausts all attempts
(`truncated = True`). This multi-step design generates rich `(state, action, reward,
next_state)` tuples where the state includes error feedback from the previous attempt —
exactly the trajectory format used in real code-repair RL training.

## What Success Means

A submission is successful when every test case in the hidden test suite passes. The
grader runs:

1. **Fixed test cases** — deterministic inputs designed to catch each specific bug.
2. **Property-based tests** — 20 deterministic inputs generated by hypothesis
   (`derandomize=True`) to prevent hardcoding specific outputs.

The expected values are only ever present in the grader process. Submitted code runs
in a separate worker container that has no `/app/hidden/` mount — it cannot read
test data at the filesystem level.

## Why This Data Would Be Useful to a Frontier Lab

**1. Direct alignment with production training tasks.**
Code repair is a core capability for coding assistants. This environment is structurally
identical to SWE-bench (the dominant evaluation benchmark for real-world code repair),
but small enough to iterate on rapidly. Training on (obs, action, reward) trajectories
from this environment directly targets the skill of fixing syntactic and logical bugs —
the most common task in developer workflows.

**2. Rich signal from multi-attempt episodes.**
Because the agent sees sanitised error feedback between attempts, the environment
generates trajectories where the agent must reason about *why* a previous attempt
failed and produce a targeted improvement. This is significantly richer than single-shot
coding benchmarks and naturally supports curriculum learning: an agent that solves
Task 1 in one attempt but needs three attempts on Task 3 provides useful difficulty-
calibrated training signal.

**3. Reward that cannot be easily hacked.**
The hidden-test grading model is specifically designed to prevent reward hacking:
- Expected values never appear in the agent's observation.
- Hypothesis property tests make hardcoding specific outputs impractical.
- The worker container's filesystem isolation prevents the agent from reading
  the test suite.

**4. Directly scalable to real codebases.**
The same grader infrastructure (worker HTTP server + hidden test suite + grader
orchestrator) can be applied to thousands of real bugs from GitHub issues with no
architectural changes. The task definition is a single Python file; adding a new task
requires only writing a buggy function, a description, and a hidden test suite.

## Three Task Difficulty Levels

| Task | Function | Bugs | Why Difficulty Level |
|------|----------|------|----------------------|
| 1 | `reverse_words` | 1 | Single two-character fix; bug visible from first failing test |
| 2 | `is_valid_brackets` | 2 | Requires understanding stack logic; bugs verified as independent |
| 3 | `compute_moving_average` | 3 | Three interacting bugs; must fix all three to pass all tests |
| 4* | `matrix_multiply` | 3 | Partial-credit reward (0.33 per category); tests category independence |

*Task 4 is the stretch task.
